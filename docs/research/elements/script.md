## ⚠ 検証で判明: 初版の「実測」は実測ではなかった(2026-08-21 検証員)

初版はこの節に「総尺 419.2s / 333字/分 / 3.71秒per unit」等を並べ、
**すべて確度A・実測**と書いていた。**これは誤りである。**

`check_long.durations()` は音声の署名が合わないとき**字数からの推定値**を返す。
初版が使った値はすべてその推定値で、`check_long` は実行のたびに
ヘッダに `尺は推定(音声は古い台本のもの)` と表示していた。初版はその表示を読み落としている。

**なぜ署名が合わないのか(check_long.py のバグ)**:

```python
# production/check_long.py  durations()
want = S.render_signature(units, scenes, out_name=out_name)   # ← bands を渡していない
```

`render.py` は `render_video(UNITS, SCENES, OUTDIR, "L001.mp4", bands=BANDS)` と呼び、
`render_video` は `bands` を署名に入れる(`shortlib.render_signature` の引数に `bands` がある)。
`check_long` 側だけ `bands=None` で署名を作るので、**BANDS を使う長尺は永久に署名が一致しない。**
検証で確認済み:

```
stored     : 1f5ae28b...   (render_video が書いたもの)
bands なし : f2c55af6...   False   ← check_long が計算する値
bands あり : 1f5ae28b...   True
```

結果として **`check_long` は長尺の秒を一度も実測できておらず、常に推定で判定している。**

**推定は約5%長い側にずれる**。`SEC_PER_CHAR_LONG = 0.17183 s/字` に対し
L001 の実測は **0.16388 s/字**(音声113本・発話のみ381.5秒 ÷ 2328字。
各ユニットの `u.speed` 上書きで平均実効 speed が 1.214 になっているぶん速い)。
**下限側のゲート(章の尺 ≥60秒 / 話速 ≥290字/分)にとってこのずれは危険な向き**で、
短い章と速い話速を、実際より安全に見せる。

- **選択肢**:

|---|---|---|---|---|
| a 問い型(現状) | 視聴者が既に頭に持っている問いをそのまま言う | 「question hook」として3型の1つに挙がる([prapermedia](https://prapermedia.com/blog/youtube-first-30-seconds-hook/) / [miraflow](https://miraflow.ai/blog/youtube-video-hooks-2026-save-first-30-seconds)) | タイトルの約束と一致させやすい。うちのショート上位(S005「なぜ実質2000円?」S001「意味ない?」)と同型 | 問いだけでは新情報がゼロの2.9秒になる |

  c はコンプライアンスで不可、b は「40秒で答えを出し切る」型と機能が重複する。

- **根拠**: 3型のうち2つが当チャンネルの制約(戦略§6の断定禁止 / 長尺は冒頭で答えを出す型)で

- **選択肢**:

| 案 | 内容 | 採用例・出典 | 長所 | 短所 |

| a 現状 | 設計100〜130、ゲート60〜150 | 自リポジトリ | 自由度がある | **設計値が守られていないことを誰も検出できない。ゲートが設計より2.5倍ゆるい** |
| b ゲートを90〜140に締める | 90秒未満を不合格 | — | 設計と検査が近づく | いまの L001 が ch2・ch3 で落ちる。書き直しが要る |

  (これをやらないと、以降どの閾値を入れても5%甘い秒で判定し続ける)。

- **根拠**: `check_long` 自身が冒頭で

- **確度**: A(ずれと署名バグは実測・再現手順あり)/ 90秒という値はC。

### C2-3 章の継ぎ目(章札の書き方)

### C2-4 章の出口の判定

- **根拠**: 「問いは判定ではない」を機械化した経緯が `07-progress.md` にあり、

### C2-5 締めの独立性

- **現状**: `longform-design.md` は「**締めは独立ブロック。章の中に埋めない**」と書いている。

| 案 | 内容 | 採用例・出典 | 長所 | 短所 |
|---|---|---|---|---|
| a 現状 | 締めを章4の末尾に置く | — | 実装が楽 | **自文書に違反している。概要欄チャプターが5行になり、締めに飛べない** |

### C2-6 章内の拍(リフック)

- **現状**: `longform-design.md` は「60〜90秒の拍は章の中に置く」と書いている。

- **決定**: **却下(初版の具体値)→ 明文化のみに縮める。**

  **検証で全章の図シーンを数えたところ、この閾値はどの章もすでに大きく上回っている。**

  | 章 | 図の異なるシーン数 | 図ユニット数 | 図シーンの切り替わり回数 |

  | 冒頭 | 4 | 6 | 3 |

  | ch3 | **3(最小)** | 12 | **3(最小)** |
  | ch4 | 9 | 22 | 8 |

  最小の ch3 でも切り替わり3回で、**提案した「最低2回」は一度も発火しない。**

  **図の差し替えは既に十分あり、足りないのは「章の中央に置く」という配置の指定のほう。**
  よって **ゲートは作らず、`longform-design.md` §5 に
  「図の更新の1回は章の中央付近(章開始+50〜70秒)に来るようにする」の一文を足すだけ**にする。
  `ask=` の問いかけカードは L001 では `sorotta` シーンに1つあるだけなので、
  章ごとに置く案b は台詞が増えて尺を押す。
- **根拠**: 「60〜90秒ごとのパターン割り込み」は確度B(`03-structure.md` の出典)。
  ただし**その拍を何で作るかは、どのソースも書いていない**。
  当パイプラインでできるのは図の差し替え・立ち絵の表情・SE の3つで、
  このうち「図は3〜5ユニット持たせ、step で数字を足す」は既存の型(`longform-design.md` §5)。
  **拍の器としていちばん安いのが図の step である。**
- **確度**: C(拍の中身に定石が見つからなかった → 自チャンネルのチャプター別維持率でA/Bテスト)。
  **初版の「最低2回」は実測と照合せずに置かれた無効な閾値だったので却下した(却下の根拠は上表・確度A)。**

## C3 会話の型

### C3-1 役割分担

- **現状**: めたん=解説役(speaker=2)、ずんだもん=聞き手。
- **選択肢**: a 解説役/聞き手(現状) / b 対等な2解説者 / c 対立(賛成役/反対役)。

  ——「こっちが得だ」と言う役を作ることになる。
- **確度**: B。

### C3-2 台詞比率

- **現状**: **めたん72 : ずんだもん41 = 64:36**(実測)。
- **選択肢**: a 64:36(現状) / b 75:25(解説役3〜5に1回の慣行から逆算) / c 50:50。
- **比較の軸**: 解説の密度 / 掛け合いのテンポ / 外部慣行。
- **決定**: **維持**(64:36)。
- **根拠**: 「魔理沙のセリフ3〜5回ごとに霊夢のセリフを挟む」
  ([YukkuriGen](https://yukkurigen.com/blog/yukkuri-kaisetsu-script-guide))なら 75:25〜83:17。
  現状はそれより聞き手が多い。**ただし C3-4 で見るとおり、ずんだもんの台詞が
  「聞き手の台詞」になっていない**ので、比率より中身を直すほうが先。
  比率そのものを動かす根拠は見つからなかった。
- **確度**: C(単一系列のスニペット)。

### C3-3 解説役の連続台詞の上限

- **現状**: **めたん連続3まで**(`duo-skit-2026-08.md` の自チャンネル規則・同文書の自己申告は確度C)。
  実測でも最大3、連続3が15回・連続2が6回・単独15回。**検証で一致。**
- **選択肢**:

| 案 | 内容 | 採用例・出典 | 長所 | 短所 |
|---|---|---|---|---|
| a 3まで(現状) | 4つ目までに聞き手を挟む | 自リポジトリ `duo-skit-2026-08.md`(確度C) | テンポが一定 | **一定すぎる。実測で連続3が15回=最頻。単調のリスク** |
| b 3〜5まで | 慣行に合わせる | [YukkuriGen](https://yukkurigen.com/blog/yukkuri-kaisetsu-script-guide) | 解説が途切れず、鎖の説明が続けられる | 聞き手の出番が減る |
| c 場所で変える | 冒頭・章の出口は2まで、章の中は5まで | — | 緩急が出る | ゲート化が複雑 |

- **決定**: **変更。上限を「3」から「章の中は5、冒頭と章の出口の前後は2」に変える**(案c)。
  ゲートにするなら: 冒頭ブロックと各章の最後3ユニットでは めたん連続 ≤2、それ以外は ≤5。
- **根拠**: 実測で連続3が15回と最頻値になっており、

  `sakubun-gensoku.md` §0 が警告する「検査工程を作文工程として使う」パターンと同じ形。
  外部慣行は3〜5(確度C)なので、上限を5に開けても慣行の範囲内。
  一方、離脱の山(冒頭)と判定の直前は掛け合いを密にしたい。
- **確度**: A(単調さの実測)/ 具体値2・5はC(A/Bテスト対象)。

### C3-4 聞き手の台詞の質

- **選択肢**:

- **確度**: A(実測のずれ。検証で再現済み: めたん72台詞平均22.7字 / ずんだもん41台詞平均22.6字)/

  「ずんだもんの台詞 + 感嘆詞始まり + face=surprised/troubled」の3点セットにする。**

  (感嘆詞始まりは41台詞中**1本**)。

### C7-4 ユニットの平均秒

  **効果量の報告は d=0.79〜0.98 と大きい**が
  ([Cambridge 第9章](https://www.cambridge.org/core/books/abs/multimedia-learning/segmenting-principle/37240877DDA0362355ADB39936027982) /

  **実験の区切りは「学習者がボタンで進める」形式**であり、
  自動再生の動画の1カットの長さとは条件が違う。**外挿できない。**

- **確度**: C(効果量はスニペット、条件が違うので行動を変えない)。

### C7-5 話速と尺の関係

- **現状**: **349字/分(実測)。** 初版の「333字/分」は推定尺から出た値で、16字/分低く出ていた。

  狙いを **「標準の上限(約330〜345字/分)に置く」**と書いている。
  **実測349字/分は、この自分の設計上限を4字/分超えている。**
- **選択肢**: a 下げる(現状) / b 上げる / c 場所で変える(冒頭を速く、判定を遅く)。
- **比較の軸**: 学術知見 / 日本語の放送基準 / 分割の原則の適用条件 / 自チャンネルの実測。
- **決定**: **維持(話速そのものは動かさない)。ただし2つを直す:
  (1) `longform-design.md` §4 の較正表を測り直す。
  (2) 「うちは標準帯の中央にいる」という自己認識を撤回する。**
- **根拠**: **ここで外部知見と自リポジトリの方針が食い違った。**
  Guo らは「**学生は話すのが速い人のほうに、より関与する**」と報告しており
  (速さそのものではなく熱意の表れという仮説つき。
  [ResearchGate](https://www.researchgate.net/publication/262393281_How_video_production_affects_student_engagement_An_empirical_study_of_MOOC_videos))、
  これは `longform-design.md` の「長尺は話速を下げる」と逆向きである。
  一方、日本語の放送基準(標準300〜350字/分)は下げる側を支持する(確度B)。
  さらに Mayer の分割の原則は「**提示が速いとき**に効く」としており、
  速さ自体を否定していない。
  **どちらが正しいかは、この環境では決められなかった。**(外部は本文未読)

- **⚠ 検証で初版の根拠が1つ崩れた**: 初版は「**333字/分は日本語の標準帯の中央なので、
  動かす根拠が無い側に倒して維持**」と書いた。**実測349字/分は中央ではない。**

  `longform-design.md` §4 が長尺の狙いとして書いた **330〜345字/分の外**にある。
  つまり「下げる方針」を掲げながら、実装は自分の目標帯を超えて速い。
  結論(維持)は変えないが、**理由は「中央だから安全」ではなく
  「上端に張り付いているが、外部が両方向に割れているので動かす向きを決められない」**に変わる。

- **⚠ §4 の較正表が再現しない**: §4 は「実効 speed と字/分の対応(この環境での実測・確度A)」として
  `1.15 → 311` / `1.25 → 340` を挙げる。L001 の平均実効 speed は **1.214**

  表から内挿すると約330字/分。**実測は349字/分**(間を除いた発話のみなら366字/分)。
  **表は約6〜11%ずれており、確度Aを名乗れない。** 測り直すまで C に落とす。
  この表は `check_long` の `SEC_PER_CHAR_LONG` の出どころでもあり、
  冒頭の⚠節で示した推定の5%のずれと同根である。

- **確度**: C(外部が両方向に割れている → 自チャンネルでA/Bテスト)/
  実測349字/分と §4 の較正ずれは A。
