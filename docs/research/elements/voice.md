## この調査で分かった最重要の6点(先に書く)

> **検証者注(2026-08-21・反証担当)**: 以下は担当検証員が
> **VOICEVOX 0.25.2 を自分で叩き直し、L001 の現物を測り直して**確かめた結果を反映済み。
> 数値が書き換わっている箇所には理由を併記した。
> なお**この環境の WebSearch は本セッションで枠を使い切っており(200/200)、
> 外部ソースの再検索はできなかった。** 到達できたのは github.com のみ(下の「検証の記録」参照)。
> したがって**外部文献に依拠した主張は、検証者が裏を取れていない**ものとして扱うこと。

1. **B1-1 の前提「実効1.21倍 = 約324〜333字/分」は、実測ではなく推定値だった。**
   `check_long.py` が出す 333字/分 は `SEC_PER_CHAR_LONG = 0.152*(1.3/1.15) = 0.1718秒/字` から
   計算した**推定**で、しかも署名不一致のため実測に切り替わっていない
   (実行すると `尺は推定(音声は古い台本のもの)` と出る)。
   焼き上がった L001.mp4 の**実測は、声だけ 366字/分・無音込み 349字/分**(検証者が再計測)。
   ゲートの許容帯 290〜360 の上端に張り付いている。**確度A**
   なお**このズレの正体は定数の較正ミスではなく、`check_long.py` の1行のバグ**だった(下の #5)。
2. **同じ `speedScale` でも、四国めたんはずんだもんより速く喋る。**
   **補正係数は 0.90 ではなく 0.87。**(検証で訂正)
   調査員の -10.4% は**1文だけ**の測定だった。検証者が
   **L001 の113文すべてを両話者・同一設定で合成し直して**測ると:
   **ずんだもん 415.7秒 / めたん 361.8秒 = 比 0.870(めたんが14.9%速い)**。
   L001 の実測でも ずんだもん 343字/分 に対し めたん **381字/分**。
   L001 は113ユニット中**72ユニット(63.7%)がめたん**(73ではない)、つまり
   **解説を担当する側が、速いほうの声で喋っている**。**確度A**
3. **B1-5 の前提「VOICEVOX出力のまま、RMS約-27dB」は誤り。**
   -27dB は `seg_XX.wav`(合成直後)の値で、`assemble()` は
   `loudnorm=I=-14:TP=-1.0:LRA=11` を**ナレーション単体と最終ミックスの2回**掛けている。
   完成品の実測は **統合 -14.2 LUFS / トゥルーピーク -0.5 dBFS / LRA 2.4 LU**。
   YouTube の目標(-14 LUFS)にはぴったり合っているが、**トゥルーピークが -1 dBTP を超えている**。**確度A**
   (実測値そのものは確度A。ただし**「上限が -1 dBTP である」という規格の側は確度C** —
   検証者は EBU R128 の一次資料にも二次資料にも到達できなかった。
   確実なのは「AAC化の後で余裕がほぼゼロ」という実測のほうで、そこを根拠にする)
4. **B1-3 の「1.05〜1.3を文脈で変える」は、実態としてほぼ機能していない。**
   L001 の113ユニットのうち `intonation` を既定(1.1)から動かしているのは
   **8ユニット(7.1%)だけ**。`pitch` と `pause_scale` の上書きは**0件**。**確度A**
   (この適用率は検証者が render.py を AST で数え直して一致。ただし
   **「1.1と1.3の差は+6.5%しかない」という調査員の測定値は再現しなかった**。B1-3 を見よ)
5. **`check_long.py` が実測に切り替わらない原因は、定数の較正ではなく1行のバグだった。**(検証で追加)
   `check_long.py:87` は `S.render_signature(units, scenes, out_name=out_name)` と呼んでおり、
   **`bands=` を渡していない**。一方 `render_video()` は `bands=bands` を含めて署名を作る。
   よって **`bands` を使う長尺は、何をどう直しても永久に署名が一致せず、永久に「推定」で判定される。**
   検証者が両方を計算して確認済み:
   `bands` 無し → `f2c55af6…` / `bands` 有り → `1f5ae28b…`(= `signature.txt` と一致)。
   **`SEC_PER_CHAR_LONG` をいくら較正しても、この行を直さない限り実測は使われない。** **確度A**
6. **完成品の音声が 96kHz AAC になっている。中間ファイルは 192kHz。**(検証で追加)
   `seg_*.wav` は VOICEVOX 出力のまま **24kHz** なのに、
   `narration.wav` と `mixed.wav` は **192kHz**、`L001.mp4` の音声は **96kHz AAC / 196kbps mono**。
   原因は `loudnorm` で、ffmpeg の loudnorm は真ピーク制限のため内部で192kHzに上げ、
   **後段に `aresample` が無いとその192kHzのまま出す**。AACの上限が96kHzなのでそこに落ちている。
   元素材の帯域は12kHzしかないので、**情報は1ビットも増えていない**。
   `narration.wav` は 154MB(24kHzなら約19MB)。**B1-5 の選択肢はこの点を1つも挙げていない**。**確度A**

## B1-1 話速

- **現状**(コードと現物から実際に読んだ値):
  - `DEFAULT_SPEED = 1.2` / `SPEED_SCALE = 1.3`(ショート) / `LONG_SPEED_SCALE = 1.15`(横型)
  - `use_landscape()` が環境変数指定なしのとき `SPEED_SCALE` を 1.15 に差し替える
  - 実際に合成へ渡る値は `(u.speed or DEFAULT_SPEED) * SPEED_SCALE`
  - L001 の `Unit.speed` 分布: 1.0が4本 / **1.05が93本(82%)** / 1.1が15本 / 1.15が1本
    → 実効 speed は 1.150 / **1.2075** / 1.265 / 1.3225
  - **実測(L001.mp4 の seg_*.wav を全部測った。検証者が再計測して字数を訂正)**:
    ずんだもん 851字 / 148.9秒 = **343字/分**、めたん 1477字 / 232.6秒 = **381字/分**、
    全体 2328字 / 声381.5秒 = **366字/分**、pad込み400.7秒 = **349字/分**
    (調査員は 855/1482/2337字 と書いていたが、`check_long.py` と同じ
     `re.sub(r"[。、【】]","")` で数えると 851/1477/2328字。秒は一致)
  - **実測(検証者・追加)**: 声だけの秒/字 = **0.1639**、pad込み = **0.1721**。
    後者は `SEC_PER_CHAR_LONG = 0.1718` とほぼ同値 — つまり
    **いまの定数は「pad込みの秒/字」を「声だけの秒/字」の位置に置いてしまっている**。
    `check_long.py` は `chars * SEC_PER_CHAR_LONG + u.pad` と pad を別に足すので、
    **padを二重に数えていることになる**。これが推定419.2秒(実測400.7秒)の正体
  - `check_long.py` の話速ゲートは `290 <= cpm <= 360`。**推定値333で合格している**
  - VOICEVOX の `speedScale` は尺にほぼ反比例(調査員の実測: `dur x speed` が 7.80〜7.91)。
    **検証者が別の文で再現**: speed 1.0/1.087/1.15/1.2075/1.3 で `dur x speed` = 
    6.005/5.994/6.097/6.015/6.060(ばらつき1.7%)。**反比例は成立している。確度A**

- **比較の軸**: 実測との整合 / ゲート帯の中での位置 / 話者間の均一性 / 8分間の疲労 /
  過去にユーザーが下した判定との整合 / 実装コスト
- **決定**: **変更**。4つを同時に入れる(検証で3→4。うち2つは調査員案を却下して差し替え)。
  1. `LONG_SPEED_SCALE = 1.15` は**維持**(ずんだもん側は実測343字/分)
  2. **めたんに話速係数 0.87 を掛ける**(調査員案の 0.90 は**却下**。下記)。
     `synthesize()` に `METAN_SPEED_ADJ = 0.87` を追加し、
     `speaker == METAN_SPEAKER` のとき `speed *= METAN_SPEED_ADJ`。実効 1.2075 → **1.050**。
     - **却下の理由**: 0.90 の根拠は**同一文1本**(6.47秒 対 5.80秒 = 0.896)だけだった。
       検証者が **L001 の113文すべてを両話者で合成し直す**と
       ずんだもん 415.7秒 / めたん 361.8秒 = **0.870**。
       別途 14文の抜き取りでも **0.875**(文ごとの比 sd 0.015、最小0.849・最大0.897)。
       **1文の測定は文ごとのばらつきの中の1点でしかなく、0.90 は3.5%の取り残しになる。**
     - **調査員自身の B1-6 の表がすでに 0.871 を示していた**(ずんだ7.91秒 / めたん6.89秒)。
       つまり同じ文書の中で 0.896 と 0.871 が併存し、決定は速いほうの数字を採っていた
  3. **`check_long.py:87` の署名バグを直す**(調査員案の「定数の較正」は**却下**)。
     `S.render_signature(units, scenes, out_name=out_name)` を
     `S.render_signature(units, scenes, out_name=out_name, bands=getattr(mod, "BANDS", None))`
     にする。これを直さない限り `bands` を使う長尺は**永久に「推定」判定**のままで、
     定数をどう較正しても実測は使われない(冒頭の6点の #5)
  4. 推定経路そのものも残るので `SEC_PER_CHAR_LONG` は較正し直すが、
     **値は 0.163 ではない**(調査員案は却下)。理由:
     `est = chars * SEC_PER_CHAR_LONG + u.pad` と **pad は別に足される**ので、
     この定数は「声だけの秒/字」でなければならない。現状の実測は 0.1639。
     **しかし上の 2.(めたん0.87)と B1-4(pause_scale 1.25)を同時に入れると、
     変更後の声だけの秒/字は 0.178〜0.182 に上がる。**
     0.163 に下げると変更後は**10%短く見積もる**ことになり、
     速すぎる台本を通してしまう。**正しくは、変更を焼いたあとの実測で 0.18 前後に置き直す**
  - この4つを入れると(検証者がユニット単位で積み直した見込み):
    L001 は **451.5秒(7分32秒)/ 309字/分**。
    `check_long.py` の他のゲート(章の尺60〜150秒・図なし連続25秒以下)も
    **検証者が再計算して全部通ることを確認済み**(章 47.6/120.9/84.9/67.5/130.6秒、図なし最長20.3秒)
- **根拠**(⚠ **検証者注: この段落の外部出典は1本も確認できていない。下の確度欄を先に読むこと**):
  日本語の話速の帯(標準300〜350字/分)は複数の独立ソースで一致している
  ([NHK式](https://diamond.jp/articles/-/56483?page=3) /
  [wis2.jp](https://wis2.jp/speaking_speed/) /
  [亀の知恵](https://kamenochie.com/kikanunotane-time-wordcount/) /
  [ナレロク](https://nareroku.com/column/goodpacenarration/))。
  ただし**「何字/分だと視聴維持率が上がるか」を示した資料は、日本語でも英語でも見つからなかった。**
  日本語のYouTube運用記事は「テンポが悪いと離脱する」としか書いておらず、数値がない
  ([ネクフル](https://necfru.com/blog/%E3%83%81%E3%83%A3%E3%83%B3%E3%83%8D%E3%83%AB%E8%A9%95%E4%BE%A1/%E5%BF%85%E8%A6%8B%EF%BC%81%E3%81%99%E3%81%90%E3%81%A7%E3%81%8D%E3%82%8B%E8%A6%96%E8%81%B4%E7%B6%AD%E6%8C%81%E7%8E%87%E6%94%B9%E5%96%84%E3%83%86%E3%82%AF%E3%80%9Cyoutube%E3%83%81%E3%83%A3%E3%83%B3/))。
  **だから今回の変更は「帯の中に入れる」ことと「話者間の段差を消す」ことだけを目的にする。**
  維持率が上がるとは書かない。
- **確度**: 実測値(343/381/366/349字/分、`dur x speed` の一定性、**めたん係数0.870**)は **A**
  (検証者が VOICEVOX 0.25.2 で独立に再測定して一致・または訂正済み)。
  **調査員の「係数0.90」は A ではなく、1標本からの推定だった → 0.870 に差し替え。**
  日本語の話速の帯(300〜350字/分)は **C に格下げ**。
  理由: 出典に挙がった6サイト(diamond.jp / wis2.jp / kamenochie.com / nareroku.com /
  toolkitslab.com / necfru.com)は**いずれもこの環境から到達できず、検証者は1本も本文を確認できていない**。
  互いに引用し合う日本語ブログ群である可能性を排除できないので、
  research-standards.md の「相互コピペは1本と数える」に従い、独立5本の要件を満たしていないと見る。
  **この帯を根拠に行動(定数)を変えてはいけない。**
  今回の変更は「話者間の段差を消す」ことだけで正当化できるので、帯は使わない。
  話速と視聴維持率の関係は **定石が存在しない → 自チャンネルのA/Bテスト**。

## B1-2 ピッチ

- **現状**: `Unit.pitch = -0.03`(全ユニット共通の既定)。
  **L001 の113ユニットで `pitch=` の上書きは0件**、つまり
  ずんだもんもめたんも、全編ずっと -0.03 の一択。
  `tts_voicevox()` が `qj["pitchScale"] = pitch` として渡す。
  - **実測(同一文・ずんだもん・fmax 700Hzで基本周波数を推定)**:

    | pitchScale | F0中央値 | 0 との差 |
    |---|---|---|
    | -0.12 | 226 Hz | -8.0半音 |
    | -0.09 | 253 Hz | -6.0半音 |
    | -0.06 | 282 Hz | -4.1半音 |
    | **-0.03(現状)** | **312 Hz** | **-2.4半音** |
    | 0.00 | 358 Hz | 0 |
    | +0.03 | 407 Hz | +2.2半音 |

    **-0.03 は「ほんの少し低め」ではなく、実測で2.4半音下げている。** 尺は変わらない。

    **検証者による独立再測定**(同一文・別のF0推定器・自己相関+放物線補間、有声ゲート付き):

    | pitchScale | F0中央値(検証者) | 0.00 との差(検証者) | 調査員の差 |
    |---|---|---|---|
    | -0.12 | 244 Hz | -8.56 半音 | -8.0 |
    | -0.09 | 281 Hz | -6.11 半音 | -6.0 |
    | -0.06 | 312 Hz | -4.30 半音 | -4.1 |
    | **-0.03(現状)** | **351 Hz** | **-2.26 半音** | **-2.4** |
    | 0.00 | 400 Hz | 0 | 0 |
    | +0.03 | 447 Hz | +1.92 半音 | +2.2 |

    **絶対Hzは推定器の違いで約12%ずれるが、半音の差は0.2半音以内で一致する。**
    このセクションが使うのは半音差なので、**結論は影響を受けない**。
    尺が pitchScale で変わらないことも再現(全条件で 4.981秒ちょうど)。
    **以後、絶対Hzは推定器依存として扱い、半音差だけを根拠にすること。**

  VOICEVOX の安全域(±0.1) / 過去の公開分との連続性 / 実装コスト

  **話者ごとの既定を導入する**: `PITCH_BY_SPEAKER = {3: -0.03, 2: -0.06}`。
  ずんだもん -0.03(据え置き) / **四国めたん -0.03 → -0.06**。
  `Unit.pitch` を明示指定したユニットはそちらを優先する(逃げ道は残す)。
- **根拠**: 低いF0が能力・信頼の判断に効くという線は、専門家が助言時に自ら声を下げる
  という実験([J Nonverbal Behav 2019](https://link.springer.com/article/10.1007/s10919-019-00307-0))
  で支持されるが、**系統的レビューは「効果は文脈と話者の性別に強く依存し、一貫しない」と結論している**
  ([Frontiers in Psychology 2025, systematic review](https://www.frontiersin.org/journals/psychology/articles/10.3389/fpsyg.2025.1495456/full) /
  [Tsantani et al. 2016](https://journals.sagepub.com/doi/10.1177/0301006616643675))。
  **合成された非実在キャラの声にこの知見がそのまま効く根拠は無い。**
  したがって今回の変更は**信頼感を狙ったものではなく、B1-6(話者の聞き分け)を成立させるための手段**として採る。
  安全域については「±0.1を超えると不自然になりやすい」という運用側の記述があり
  ([テックジム VOICEVOX上級者向けガイド](https://techgym.jp/column/voicevox/))、-0.06 はその内側。
- **確度**: pitchScale と F0 の**半音差**の対応表は **A**(検証者が別実装で再現)。
  **絶対Hzの列は C**(推定器で12%動く。根拠に使わないこと)。
  低い声と信頼の関係は **C**(系統的レビューが一貫しないと明言している。行動を変える根拠にしない)。
  安全域±0.1 は **C**(単一ソース)。
