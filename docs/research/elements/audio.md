## B2-2 ダッキング

- **現状**: `[bgv][narb]sidechaincompress=threshold=0.015:ratio=6:attack=8:release=300:makeup=1`

  ffmpeg の一次資料(`ffmpeg -h filter=sidechaincompress`、ローカル実行)による既定値と比べる:

  | パラメータ | 現状 | ffmpeg既定 | 現状は既定の |
  |---|---|---|---|
  | threshold | 0.015(-36.5 dBFS) | 0.125(-18.1 dBFS) | 1/8(=18dB低い) |
  | ratio | 6 | 2 | 3倍 |
  | attack | 8 ms | 20 ms | 0.4倍 |
  | release | 300 ms | 250 ms | 1.2倍 |
  | knee / detection / mix | 既定 | 2.83 / rms / 1 | — |

  **3方向すべてで既定より強い方に振ってある。** 実測のダック量は **15.6 dB**
  (静止時 -41.7dB → 発話中 -57.3dB)。ナレーションのピークが -1.0 dBFS まで来るので、
  ピーク時の理論ゲインリダクションは (36.5-1.0)×(1-1/6) = **29.6 dB** に達する。

- **選択肢**:

  | 案 | 内容 | 採用例・出典 | 長所 | 短所 |
  |---|---|---|---|---|
  | A 現状維持 | th0.015 / r6 / a8 / rel300 | ffmpeg-user ML やチュートリアルに th0.015〜0.03・ratio4〜15 の例がある[5] | 声は絶対に埋もれない | ダック15.6dB。B2-1と合わせてBGMが消える |
  | B 既定寄りに戻す | th0.03 / r2 / a20 / rel400 | ffmpeg既定(th0.125/r2/a20/rel250)に近い。VO推奨の attack≈20ms[1] | 実測ダック **8.7dB**。放送VOの標準帯 | 声の子音が少しBGMと重なる |
  | C `mix` でダック量に上限 | r6 のまま `mix=0.5` を足す | ffmpeg の mix(0〜1、既定1)はドライ/ウェット比。GRに頭打ちを作れる | 強い設定のまま深さだけ抑えられる | 挙動が直感的でない。実測で追い込む必要がある |
  | D ダッキングを外す | 固定音量のみ | Mayer流の「BGMは一定の環境音」設計 | 実装が単純。ポンピングが原理的に起きない | 数字を読む所で声が沈む可能性 |

- **比較の軸**: 声の明瞭度 / ダック量が定石帯(3〜10dB)に入るか / ffmpegの既定からの逸脱度 /
  「止め」の完全ミュート実装との相性 / 実装コスト

- **決定**: **変更。`threshold=0.015 → 0.03`、`ratio=6 → 2`、`attack=8 → 20`、`release=300 → 400`。**
  makeup=1 は維持。実測ダック量 **8.7 dB**(volume=0.50 と組み合わせて 静止時-31.2dB / 発話中-39.9dB)。

  release を 300→400 にするのは、`LONG_STOP_PAD=0.5` 以上の「止め」は別途 `volume=0:enable=...`
  で完全に切っているため、300msで戻す必要がないから。文と文の間(pad=0.15)でBGMが
  戻りきらない方がポンピングしない。

- **根拠**:
  - ffmpeg の既定値は `ffmpeg -h filter=sidechaincompress` の出力(一次資料・ローカル実行)。
    threshold 0.125 / ratio 2 / attack 20 / release 250。
  - VOのダッキングは「1〜3dB」「6〜8dBを超えたらやりすぎ」という記述が複数。
    <https://www.sweetwater.com/insync/what-is-sidechain-compression/>
    <https://mastering.com/sidechain-compression-guide/>
    <https://emastered.com/blog/sidechain-compression>
  - 一方 VO 実務のffmpeg例は threshold 0.015〜0.03・ratio 4〜15 を挙げており、
    こちらは「音楽ミックス」ではなく「放送ダッキング」の文脈。
    <https://www.ffmpeglab.com/articles/ffmpeg-audio-mixing-amix-guide.html>
    <https://ffmpeg.org/pipermail/ffmpeg-user/2018-August/040933.html>
  - 両者の間を取って **8〜10dB** を狙った。attack 20ms は VO 推奨(音楽ミックス側ソース)と

## B2-3 曲調

## B2-4 BGMの変化

- **現状(実測)**:
  - `BGM_VARIANTS` は **3種**(4種ではない)。`bgm_variant = seed % len(BGM_VARIANTS)` で

  - **検証員の補正**: 厳密には「同じ11.16秒」が繰り返されるのは**音程のある層だけ**である。
    ハットのノイズ・ヒス・クラックルは `rng` を進めながら生成されるので毎回違う波形になる。

     - 章2: + キック
     - 章3: + ハット(swing 0.66)
     - 章4: 全部 + コード周波数を `2**(2/12)` 倍(全音上げ)

  4. 章境界には **0.8秒のクロスフェード**(章札の切り替わりに隠す)。
  5. `render_video` は既に `bands`(章の開始ユニット番号)を持っているので、

- **根拠**:
  - 「4〜8小節が定番。8小節を超えると反復疲労のリスクが上がる。長尺では単一ループに

  - 「BGMの切り替えは画面の切り替え(章・場面・時間経過)に同期させると、視聴者の注意が
    映像の変化に向くのでBGMの変化が目立たない」
    <https://omniweb.jp/m96/> <https://furwa.co.jp/specialty/bgm-timing-tips/>
  - **どちらも単一〜二次ソースで、一次資料に当たれていない**(omniweb.jp は proxy 遮断)。
    実測(11.16秒×35.9回、変化は全尺の0.75%)だけが確度Aの事実。

- **確度**: 現状の実測 **A**。「章ごとに編成を変えると維持率が上がる」 **C**。
  実装コストが低い(numpy の条件分岐だけ)ので入れるが、

  | B 3種に減らす | puchun を長尺の語彙から外す | 「少数を使い回す」[13] | 意味の対応が覚えやすい | ショート側では puchun がフリーズ演出に効いている(縦型では残す) |
  | C 増やす | 章頭の whoosh / ページめくり / 正解チャイム 等 | ゆっくり実況の定番は10種以上[11] | 表現の幅 | 合成の実装コスト。使い分けが曖昧になると逆効果 |
  | D 種類は増やさず「意味と音の対応」を固定 | pop=提示 / don=結論 / impact=驚き / puchun=フリーズ、を運用ルールに明文化 | 「選び抜いた合成トーンを**体系的に**使うことが、その音を記憶のアンカーにする条件だった」[13] | コスト0。効果の根拠が最も具体的 | 台本側の規律が要る |

- **比較の軸**: 意味の一貫性(記憶のアンカーになるか) / 認知負荷 / 実装コスト /
  縦型と横型での使い分け / 音の被り(他チャンネルとの差別化)

- **決定**: **維持(種類数は4のまま)+ D を追加。**
  `docs/research/longform-design.md` と `templates/` に、この対応表を明文化する:

  | SE | 意味 | 置く場所 |
  |---|---|---|
  | pop | 新しい値・テロップの提示 | 数値カード・章札・新情報の1文目 |
  | don | 損得の判定・結論 | 各章の出口の判定1文 |
  | impact | 驚き・前提のひっくり返し | 冒頭40秒の答え、例外の提示 |
  | puchun | フリーズ演出 | **縦型ショートのみ**。長尺では使わない |

  種類を増やす方向は採らない。増やすなら「章頭の whoosh」1種だけを候補に残す。

- **根拠**:
  - 「体系的に選ばれた合成トーンの適用が、学習者が音の使い方のパターンを認識するために
    決定的であり、それによってこれらのトーンが記憶のアンカーとして機能した」
    <https://edtecharchives.org/journal/423/8392>
  - 「効果音は音を足すためのものではなく、視聴者に『ここで何が起きたか』を伝える補助線。
    切り替え・強調・操作の3種を中心に考えると整理しやすい」
    <https://tadaoto.com/blog/how-to-add-sound-effects-to-video/>
    <https://mobunikomiudon.com/se-kotsu/>
  - **ソースは実質1本(EdTech研究)+日本語のノウハウ記事**。
    「4種が最適」という定石は見つからなかった。見つかったのは
    「数より一貫性」という方向だけ。

- **確度**: 「数より一貫性が効く」 **C**(単一の研究記事。本文未確認)。
  「少数を使い回す」という方向 **C+**(初稿は B。日本語ノウハウ記事2本が一致するだけで、
  検証員も本文を取得できていない。ソース2本で B は名乗れない)。
  「4種という数字」に根拠はない → **定石は存在しない。当チャンネルの運用で固定する。**

  意味対応表の明文化(案D)は**確度に関係なく実施してよい**。コスト0で、
  「効かなかった」場合の損失も無く、台本工程の判断を減らす効果だけが確実にあるため。
  ただし *効果* を主張してはいけない。

  > (SEがどのユニットに付いているかと章境界の対応まではコードから機械的に取れない)。
  > **数えていないルールをゲートにしない。**

    <https://www.ncbi.nlm.nih.gov/pmc/articles/PMC11061496/>

    <https://www.ncbi.nlm.nih.gov/pmc/articles/PMC11274038/>

    <https://detail.chiebukuro.yahoo.co.jp/qa/question_detail/q13250498173>

- **確度**: 現状の実測 **A**(検証員が render.py を構文解析して再現。

## B3-3 SEの音量

- **現状**: `[N:a]volume=0.55[se]`。その前段で `synth_se_track` がトラック全体を
  0.5倍している(ピークが1.0を超えたときだけ先に正規化)。

  実測(各SEを単体合成し、`volume=0.55` 適用後のピーク):

  | SE | 単体ピーク | volume=0.55後 | ナレーションのピーク(-1.0 dBFS)との差 |
  |---|---|---|---|
  | pop | -12.2 dB | -17.4 dB | **-16.4 dB** |
  | don | -7.1 dB | -12.3 dB | **-11.3 dB** |
  | impact | -6.9 dB | -12.1 dB | **-11.1 dB** |
  | puchun | -6.0 dB | -11.2 dB | **-10.2 dB** |

- **選択肢**:

  | 案 | 内容 | 採用例・出典 | 長所 | 短所 |
  |---|---|---|---|---|
  | A 現状維持(0.55) | 声比 -10〜-16dB | (現状) | 定石帯 -5〜-20dB のほぼ中央 | 変更しない理由の明示が要る |
  | B 上げる(0.75) | 声比 -7〜-13dB | 映画のSFXは -10〜-20dB、スパイクで-8dB[16] | pop がもっと聞こえる | don/impact が耳に刺さる帯に近づく |
  | C 下げる(0.40) | 声比 -13〜-19dB | ゆっくり系の控えめ運用 | 落ち着く | pop が -20dB を割り、実質聞こえなくなる |
  | D 種類ごとに個別の音量を持つ | pop だけ 0.75、don/impact は 0.55 | 種類別に混ぜるのが本来のミックス | pop と don の意味差を音量で作れる | パラメータが増える |

- **比較の軸**: 声のピークとの差が定石帯(-5〜-20dB)に入るか / BGMより十分上か /
  種類ごとの意味差(pop=控えめ、don=強い)が保たれるか / 実装コスト

- **決定**: **維持。`volume=0.55` を変えない。**
  理由は実測が定石帯のど真ん中にあるため。B2-1でBGMを -39.9dB(発話中)まで上げても、
  SEのピークはそれより **27dB上** なので埋もれない。
  pop が -16.4dB と控えめ、don/impact が -11dB と強いのは意図どおり(pop=提示の合図、
  don=結論の打点)なので、種類別音量(案D)も不要。

- **根拠**:
  - 「話し声と一緒に効果音を使うなら、効果音の音量は-5dB〜-20dBの間」
    <https://tadaoto.com/blog/how-to-add-sound-effects-to-video/>
    <https://creatorways.jp/audio-levels-for-video/>
  - 映画のミックス仕様例では SFX -10〜-20dB、スパイクで-8dB、ダイアログ -12〜-15dB。
    <https://www.mordego.com/postproduction/how-to-mix-your-movie-set-your-mixing-workstation-how-loud-dx-bg-sfx/>
    <https://www.wevideo.com/blog/how-to-set-audio-levels>

- **確度**: 実測 **A**。目標帯(-5〜-20dB) **B**。

- **監視項目(今回の調査で見つけた別の問題)**:
  `synth_se_track` の末尾(`shortlib.py:509-513`)は「トラックのピークが1.0を超えたときだけ
  全体を正規化し、そのあと一律0.5倍」という実装。
  **SEが重なった動画だけ全体が小さくなる**非決定性がある。
  現状はSEの間隔が22秒なので発生しないが、B3-2で頻度を上げると起きうる。
  正規化ではなく `np.clip` かソフトリミッタに変えるべき。確度A(コードを読んだ事実)。

  > **検証員の確認**: この指摘は正しい。実装は
  > `peak = np.abs(track).max()` / `if peak > 1.0: track = track / peak` / `track = track * 0.5`。
  > 全トラックに掛かるスカラー除算なので、**1箇所でSEが重なっただけで動画全体のSE音量が下がる**。
  > しかも下がり幅は台本次第で毎回変わるため、B3-3で測った声比 -11〜-16dB が保証されなくなる。
  > **このドキュメントで唯一、外部ソースをまったく必要とせずに実施できる修正**であり、
  > 優先度は B2-1/B2-2 と同格。ただし現行の全動画は間隔22秒で発生していないので、
  > **既存動画の再レンダリングは不要**(この1件だけなら音は変わらない)。

## B3-4 SEの同期

- **現状(実測)**: `render_video` は
  `se_events.append((elapsed + (0.07 if u.cover else 0.0) + u.se_at, u.se))`。
  `se_at` の既定は **0.0** なので、**SEはユニットの先頭で鳴る**。

  一方、図は `anim` 秒かけて動く。L001 の18本のSEを調べた結果
  (**検証員が render.py を括弧対応で構文解析して数え直した値**。初稿の内訳は誤りだった):

  | 状況 | 本数(訂正後) | 初稿 |
  |---|---|---|
  | `anim=0`(静止画。SEと画が一致) | **9** | 10 |
  | `anim=1.4` で `se_at=0` → **着地より1.40秒早い** | **8** | 7 |
  | `anim=1.6` で `se_at=0.32` → **着地より1.28秒早い** | **1** | 1 |

  つまり **18本中9本が、図の着地より1.28〜1.40秒早く鳴っている**(初稿は「8本」)。
  「se_atで着地に同期」という前回の現状記述が事実に反する、という結論は変わらない。

  > **検証員の訂正(声との位置関係)**: 初稿の
  > 「VOICEVOX の各セグメントは前後に約0.15秒の無音を持つので、`se_at=0` のSEは
  > 声より0.15秒早い位置に落ちる。声との関係では自然」は**誤り**である。
  >
  > - `silencedetect=n=-50dB` で実測した `seg_00/05/40.wav` の**先頭無音は 0.055〜0.085秒**。
  >   0.15秒ではない。
  > - 0.15秒という数字は `Unit.pad` の既定値(`shortlib.py:190`)であり、
  >   **ナレーションの後ろに足す間**である。VOICEVOX が持つ前の無音ではない。
  >   調査員はこの2つを取り違えている。
  > - したがって `se_at=0` のSEが声より先行するのは **約0.06〜0.09秒**しかない。
  >   `pop`(0.09秒)はぎりぎり収まるが、**`don`(0.28秒)は声の頭に確実に被り、
  >   `impact`(2.2秒)は声の上を2秒間鳴り続ける**。
  > - これは案Bの短所として書かれた「SEが声の途中に落ちる」が、
  >   **現状すでに起きている**ことを意味する。案Bの短所の書き方は成り立たない。

- **選択肢**:

  | 案 | 内容 | 採用例・出典 | 長所 | 短所 |
  |---|---|---|---|---|
  | A 現状維持 | 常にユニット頭 | (現状) | pop(0.09秒)は声の頭の無音(**実測0.06〜0.09秒**)にほぼ収まる | 図の着地とは最大1.4秒ズレる。**don/impact は声の頭の無音に収まらず、既に声に被っている** |

  | C anim を短くする | don/impact を持つユニットの `anim` を 1.4〜1.6 → **0.6** に | 冒頭40秒で答えを出す長尺設計と整合 | 先行が 1400ms → 600ms に縮む | 図の動きが速くなる。**声との衝突は解消しない**(SEはユニット頭のまま)。`impact` は2.2秒鳴るので効果が出ない |
  | D 種類で使い分け | pop はユニット頭(字幕はユニット頭に出るので一致)/ don・impact は着地 | 意味の違いをそのまま同期方針に | 理屈が通る | 台本側で anim と se_at の両方を意識する必要 |

- **比較の軸**: 音と映像のズレ(ITU-R の閾値) / 声との衝突 / 台本の書きやすさ /
  機械ゲートで検出できるか

- **決定(検証員が修正)**: **L002 での試作にとどめる。ゲート化は却下。**
  1. `pop` は `se_at=0` のまま維持。**字幕はユニット頭に出るので、映像イベントと既に一致している。**
     これは変更なしなので確度に関係なく確定でよい。
  2. **L002 で `don` / `impact` のユニットの `anim` を 0.6 に揃えた版を作り、現行と目視で比べる。**
     効くと分かってから `templates/` に書く。
  3. どうしても長い `anim` で着地を打ちたいときだけ `se_at = anim - 0.05` を明示指定できる、
     という**選択肢の存在**だけ `templates/` に書く(推奨はしない)。

  > **検証員による却下**: 初稿の
  > 「`don`/`impact` のユニットは anim<=0.6 を既定にする」+「`check_long.py` にゲートを足す」は
  > **却下する**。理由は3つ。
  >
  > 1. **落ちる本数の見積もりが違う。** 初稿は「L001 の8本はこれで落ちる」と書いているが、
  >    提案されたゲート条件 `se in ("don","impact") かつ anim - se_at > 0.8` に該当するのは
  >    **4本だけ**である(`don` で anim=1.4 が3本、`impact` で anim=1.6/se_at=0.32 が1本)。
  >    残り5本は `pop` で、規則自身が除外している。**自分のゲートが何を落とすか数えていない。**
  > 2. **確度Cの主張でゲートを作っている。** 同じ節の確度欄が
  >    「成長アニメの映像イベントが動き出しか着地かには定石が見つからなかった」

  >    「着地に合わせる」という概念自体が成立しない。
  >    `impact` を含む規則は、まず音の長さの側を設計しないと意味を持たない。

    <https://support.biamp.com/Tesira/Video/Lip_Sync_and_Delay_Equalization_in_TesiraLUX>
    <https://www.thebroadcastbridge.com/content/entry/20119/audio-for-broadcast-synchronization>
    <https://www.testdevlab.com/blog/how-to-test-audio-video-sync>
    (※ ITU の原文および Wikipedia は本環境の proxy で遮断。二次引用。)
  - 「効果音のタイミングは、視聴者に『ここで何が起きたか』を伝える補助線」
    <https://tadaoto.com/blog/how-to-add-sound-effects-to-video/>

- **確度**: 実測(18本中**9本**が1.28〜1.40秒早い) **A**(検証員が数え直し)。
