# 焼き上がりを測ってわかったこと(2026-08-22)

**確度A = 自分で測った値**。この文書の数字はすべて、このリポジトリの成果物
(L001.mp4 / S020.mp4 / S030.mp4 と output/work/ のフレーム)を実際に測った結果。
外部の一次資料に当たれない環境なので、**測れるものは測る**を確度Aの定義にしている。

測るのに使ったもの: PIL(フレームの画素差)、ffmpeg の loudnorm 解析、
render.py の UNITS(話者・話速・SE・止め)。

---

## 1. 画面が15〜20秒まったく変わらない区間があった(→ 直した)

**測りかた**: `anim=0.0` で同じ場面が続く区間の、最初のフレームと最後のフレームを比べる。
字幕帯の影響を除くため、上から74%(=字幕より上)だけを見た。

| 区間(L001) | ユニット数 | 字幕より上の画素の変化 |
|---|---|---|
| uchiwake | 5 | **0.00%** |
| sashihiki | 5 | **0.00%** |
| nikai | 5 | **0.00%** |
| pat1 | 4 | **0.00%** |
| jibun2 | 5 | **0.00%** |
| nashi | 4 | **0.00%** |
| riyuu2 | 4 | 4.69% |

つまり**19.6秒のあいだ、動いているのは字幕だけ**だった。
L002(書き直す前)は最長25.0秒、全体の33%が14秒を超える静止だった。

**原因は2つ重なっていた**:

1. `chara="none"` の図ユニットでは立ち絵が消えるので、口パク・体の揺れも無くなる。
   longform-design の「図が主役のユニットは立ち絵を消す」は正しいが、
   **消したあとに何も動くものが残っていなかった**。
2. リッチ背景の「漂う¥」が、実質まったく動いていない(次項)。

**直しかた**: 同じ図のまま `highlight` / `reveal` / `lit` を進める場面を用意して、
話の進みに合わせて画面が変わるようにした。台本の言葉は1文字も変えていない。

- L001: uchiwake→uw_a/uw_b/uw_c、sashihiki→nokoru、nikai→nikai_a/nikai_b、
  pat1→amari、jibun2→jibun2_a/jibun2_b
- L002: be1/be2/be3(棒を1本ずつ増やす)、za1/za2、ky1/ky2(曲線の reveal)、
  tejun1/tejun2(チェックリストの点灯)、up1a/up2/sou35/hy1/uchi1b/kariru/sog2/sog3

**ゲートにした**: `check_long.py` の「静止の連続」(14秒超で不合格)と
「静止の割合」(20%超でWARN)。**量を増やしても通らない**種類のゲートなので不合格側に置いた。

## 2. 背景の漂う¥は、動いているうちに入っていなかった

`_draw_rich_layers` は ¥ を `alpha=0.05`、毎秒 x方向 0.010(画面幅の1%)で動かす。
実測すると、立ち絵なしのユニット内で先頭フレームと末尾フレームの
**最大画素差が 8/255(約3%)、差のある画素は 0.586%** しかない。
閾値8で数えるとちょうど消える大きさで、目では見えない。

`DRIFT_FPS = 4` でフレームを刻んでいるので**エンコード時間だけは増えている**。
「常に動く画面」を作るつもりの仕組みが、コストだけ払って効いていなかった。

**判断**: 濃くする(alpha を上げる)方向には振らなかった。図の読みやすさを削るため。
代わりに項1の「図そのものを進める」で動きを作った。¥の設定はそのまま残してある
(背景の質感としては効いている)。

## 3. 真のピークにヘッドルームが無い(→ 直した)

**測りかた**: `ffmpeg -af loudnorm=...:print_format=summary -f null -`

| 動画 | 統合ラウドネス | 真のピーク | LRA |
|---|---|---|---|
| L001 | -14.2 LUFS | **-0.2 dBTP** | 2.5 LU |
| S020 | -14.1 LUFS | **-0.6 dBTP** | 1.4 LU |
| S030 | -14.3 LUFS | **-0.8 dBTP** | 1.3 LU |

統合ラウドネスは YouTube の -14 LUFS にぴたりと合っている(ここは直す必要なし)。
問題は真のピーク。`assemble()` は `TP=-1.0` と指定しているのに -0.2 までしか下がっていない。
loudnorm の1パス動的モードは真のピークを保証せず、そのあとの AAC エンコードが
サンプル間ピークを持ち上げるため。**ヘッドルームが無いと、YouTube側の再エンコードで歪む。**

**直しかた**(実測でリミッタの値を決めた):

| チェーン | 統合 | 真のピーク |
|---|---|---|
| いまのまま(`TP=-1.0`) | -14.2 | -0.2 |
| `TP=-1.5` + `alimiter=limit=0.841` | **-14.3** | **-0.6** |
| `TP=-1.5` + `alimiter=limit=0.750` | -14.6 | -0.9 |
| `TP=-1.5` + `alimiter=limit=0.668` | -15.0 | -1.7 |

**0.841(≒ -1.5 dBFS)を採用**。これ以上絞ると統合ラウドネスが -14 を割って、
今度は「他チャンネルより音が小さい」問題(ループ㉞)が戻ってくる。
**改善は0.4dBぶんで、大きくはない。** それでもコストがゼロなので入れた。

## 4. 測ったが、直さなかったもの

- **LRA 1.3〜2.5 LU**(放送の話し声は4〜8が普通)。音の起伏が小さい。
  ただし原因は「TTSの音量が最初から一定」で、広げると小さい所が聞こえなくなる。
  **自チャンネルの維持率で検証する仮説として置く**(確度C。確度Cで行動を変えない)。
- **四国めたんの発話が L001 で65%・L002 で58%**。ショート30本はずんだもんなので、
  ショートから来た人には別チャンネルに見えるおそれがある。
  ただし「説明する側=めたん / 聞く側=ずんだもん」は寸劇の型として素直で、
  duo-skit-2026-08.md の設計どおり。**変えるなら型ごと変える話**なので保留。
- **話者交代は 1.4〜1.6ユニットに1回、最長でも4〜5ユニット連続**。これは健全。
- **SEの密度 L001 15.9% / L002 11.8%**(round1調査の目安は9%)。
  L002は書き直しで自然に下がった。L001は次の作り直しで見る。
- **止め(pad≥0.5)は両方5個**=章の出口4つ+冒頭。設計どおり。

## この回の教訓

**いちばん効いた調べかたは、作ったものを測ることだった。**
静止19.6秒も、真のピーク-0.2dBTPも、企画書や台本をいくら読んでも出てこない。
どちらも「出来上がったファイルを開いて数える」だけで出た。

そして**静止の件は、自分で足したゲートの副作用でもあった**。
「数字は図の上で言う」を通すために同じ図へユニットを積み、その結果画面が止まった。
ゲートを足すときは、**そのゲートを通すいちばん安いやり方**が何を壊すかまで見ること。

# 追記: サムネイルを実際の表示サイズで見て、初めて見つかったもの

## 5. サムネの金の行が、左右の立ち絵を突き抜けていた(→ 直した)

**きっかけ**: サムネは 1920×1080 で作っているが、YouTube が出すのは
PC のフィードで 360×202、スマホで 246×138、関連動画で 168×94。
**その大きさに縮めて見た**ところ、金色の1行が両端で立ち絵に潰されていた。

**測りかた**: 縮小画像で異変に気づいたあと、原寸で画素を色相で分けて範囲を測った。
金の行の高さ(y 62〜74%)で、

| | 範囲 |
|---|---|
| 左の立ち絵(ずんだもん) | x 0 〜 **25.5%** |
| 右の立ち絵(めたん) | **77.3%** 〜 100% |
| 空いている帯 | 25.5% 〜 77.3%(幅51.8%) |
| **金の行「もうけた株の税金が消える。ただしNISAは別」** | **10.6% 〜 89.4%** |

両端が立ち絵に乗っていた。とくに右端の「ただしNISAは別」はめたんの顔に重なっていて、
**読めないうえに、事故に見える**。

**なぜ全ゲートを通ったのか(ここが本題)**

`check_overlap.py` は立ち絵との重なりを見るゲートで、ちゃんと存在していた。
通った理由は2つ、どちらも**二人会話にしたときの直し忘れ**だった。

1. `zones_for_format()` が、横型では `CHARA_RECTS["br"]`(右下)**しか**返していなかった。
   横型に立ち絵が1体だった頃の名残で、**左に増えた1体を誰も見ていなかった**。
2. カバー場面は `has_chara = key not in cover_keys` で立ち絵チェックから外していた。
   ところが `make_thumbnail()` は**カバーの上に立ち絵を2体描く**ので、
   「カバーに立ち絵は無い」という前提が、サムネに限っては成り立っていなかった。

**直しかた**

- `scenes_long.cover()` の金の行を `max_w=0.48` にした。
  画面幅(既定0.92)ではなく**立ち絵のあいだ**に収まるまで縮める。
  実測で L001 は 26.3%〜73.8%、L002 は 31.0%〜68.8% に収まった。
  文字だけを短くする直しかたも試したが、それだと**次に長い文を書いた人がまた踏む**。
- `check_overlap.py` の横型の禁止領域を、左右**両方**の立ち絵にした。
- L001 のコピーも短くした(「もうけた株の税金が消える。ただしNISAは別」→「損が税金を消す。NISAは別」)。
  サムネの補助行は、そもそも短いほうが小さい表示で効く。

**残っている穴(直していない)**: サムネの立ち絵の矩形は各 render.py の
`make_thumbnail()` にべた書きで、`CHARA_RECTS` とは別物。ゲートはまだ
「動画中の立ち絵」しか見ていない。**サムネ専用の矩形を shortlib に移して
ゲートから引く**のが本筋だが、いまは金の行を空き帯に収める側で塞いである。

# 追記2: 「二人会話にしたときの直し忘れ」が3か所あった

サムネの1件を追いかけたら、**同じ形の欠陥が3か所**出てきた。どれも
「立ち絵が右の1体だけだった頃の前提」がコードに残ったもので、
しかも**ゲート自身が同じ前提だったので、機械では気づけなかった**。

| # | どこ | 1体だった頃の前提 | 実測 |
|---|---|---|---|
| 1 | `check_overlap.zones_for_format()` | 横型の立ち絵は右下だけ | 左の立ち絵は**動画本編でも無防備**だった |
| 2 | `scenes_long.cover()` の金の行 | 画面幅いっぱい(max_w=0.92)に伸ばしてよい | 文字が幅の10.6%〜89.4%、空き帯は25.5%〜77.3% |
| 3 | `scenes_long` の `card`/`hero` の中心 | (PLOT_L+PLOT_R)/2 = **0.415**(左が空いているので寄せる) | 幅0.66だと左端が**0.075**。絵は0.180から始まる |

3の中心座標がいちばん根が深い。左に立ち絵が無かったから左へ寄せていた設計で、
**その前提が消えたのに数字だけ残った**。`_duo_center_fit()` を足して、
立ち絵があるあいだは絵と絵のまんなか(0.500)・幅0.576(→ 0.212〜0.788)にした。

## ここから引く教訓

**画面の構成を変えたら、その構成を前提にしている場所を全部たどる。**
「二人会話にする」は台本と描画の話に見えて、実際には

- 立ち絵の座標(shortlib)
- 文字の中心と幅(scenes_long の cover/card/hero)
- **重なりを見るゲートの禁止領域**(check_overlap)
- ゲートが「立ち絵が出るか」を判定する方法(units の chara を見ていなかった)

の4か所にまたがっていた。1か所目だけ直して残り3か所を忘れると、
**ゲートは緑のまま、出荷物だけが壊れる**。今回はそれが実際に起きた。

## もう1つの落とし穴: 署名がレイアウトを見ていない

`render_signature()` は units と **SCENES のキー**しか見ない。だから
`scenes_long.py` のレイアウトを直しても署名は変わらず、再開キャッシュが効いて
**古いレイアウトのフレームが残ったまま「再レンダリング済み」の動画が出る**。
今回は両方の `output/work` を消して一から焼き直して回避したが、
**描画モジュールの中身も署名に入れる**のが本筋(次にやる)。
