## この調査で分かった最重要の3点(先に書く)

1. **A3-7 縁取り**: `stroke_fx()` の `fatten=2.0`(文字と同色の太らせストローク)が
   漢字の内側の白場を塞いでいる。**方向は再現した**が、調査員の「4個 → 0個」は再現しない。
   別実装での再計測(40pt・6字・閾値3種)では「確」が **7個 → 1個**、
   インク被覆は **0.403 → 0.502**。字によっては逆転する(「段」は 1個 → 4個)。
   **確度A(fattenがcounterを埋める方向)/ 個数の絶対値は閾値依存で再現性なし**
2. **A3-14 出現演出**: `pop=1.06` は `anim>0` のユニットの先頭1フレームにしか渡らない。
   L001 の **113ユニット中59(52%)は `anim=0` なので pop が一度も起きない**。
   起きても持続は `1/fps = 0.05秒`。**演出は実質存在しない**。**確度A**
3. **A3-10 強調色**: `【】` の黄色強調は **L001・L002 とも使用0件**。S012以降のショートも全部0件。
   S001〜S009 では1本あたり10〜14個使っていた。**機能が死んでいる**。**確度A**
   ただし「だから復活させる」という**行動**のほうは確度C(下記 A3-10 の⚠検証)。

## A3-2 ウェイト

- **現状**: **タスク記述の「Bold 700、black指定はフォールバック」は誤り。実際は逆。**
  実測(`font_manager` の登録内容を出力して確認):
  - `Noto Sans CJK JP` weight **900** ← `NotoSansCJK-Black.ttc`
  - `Noto Sans CJK JP` weight **700** ← `NotoSansCJK-Bold.ttc`
  - `plt.rcParams["font.weight"] = "bold"`(=700)だが、
    `draw_rich_line()` の既定引数が `weight: str = "black"` で、字幕描画は必ずこれを通る。
  - **したがって字幕に実際に出ているのは Black(900)**。rcParams の bold は字幕には効いていない。
- **選択肢**:

  | 案 | 内容 | 採用例・出典 | 長所 | 短所 |
  |---|---|---|---|---|
  | ① Black 900(現状) | 最太 | ゆっくり界隈は太ゴシックが定番([いいフォント](https://goodfreefonts.com/4953/)) | 縁取りと帯の上で最も強い。遠くから読める | 漢字の線間が詰まる。縁取りを足すと内側の白場が消える |
  | ② Bold 700 | 一段細い | [Open Sans は Bold ではなく Semibold を推す](https://circletranslations.com/blog/subtitle-fonts-top-10-fonts-for-subtitles-and-closed-captions)(「Boldはchunky/crowdedになる」) | 白場が広い。実測で「確」の最大白場が 43px → **48px**(+12%) | 帯や図の上でやや弱い |
  | ③ 900 のまま、縁取り側を直す | ウェイトは触らず `fatten` を外す | 自パイプラインの実測 | 白場が0個 → **4個**に戻る。他の描画に副作用が無い | 根本の「極太は詰まる」性質は残る |

- **比較の軸**: 漢字の内部白場(counter)が残るか / 帯・図の上での強さ / 変更の副作用の広さ
- **実測(40pt・「確」を80×62pxで切って計測。⚠ 反証担当が別実装で再計測した値に差し替え)**:

  | 条件 | インク被覆 | 字内の白場の数 | 最大白場の面積 |
  |---|---|---|---|
  | **現状(black900 + fatten2.0)** | 0.502 | **1** | 47px |
  | black900 + fatten 0 | 0.403 | **7** | 95px |
  | bold700 + fatten 0 | 0.356 | **6** | 120px |
  | bold700 + fatten2.0 | 0.464 | **4** | 52px |

  → **潰れの主因はウェイトではなく `fatten`。** インク被覆に効く量は
  fatten が +0.10、ウェイト(900→700)が +0.05 で、**fatten のほうが2倍効く**。

- **⚠ 検証(反証担当)**: 調査員の原表(被覆 0.439/0.314/0.277/0.407、白場 0/4/4/1)は
  **再現できなかった**。順序と方向は同じだが絶対値が違う。原因は切り出し枠と
  インク判定のしきい値で、白場の個数はしきい値を 60/120/180 と振ると 2/1/1 と動く。
  さらに**字によって逆転する**(「段」は fatten0 で1個、fatten2.0 で4個)。
  したがって「白場の個数」は**判断材料に使えない**。使えるのはインク被覆(単調)と目視。
  → **A3-7 の決定は支持するが、その根拠は「白場が0個になる」ではなく
  「fatten がインク被覆を +0.10 押し上げ、counter の面積を半分以下に潰す」に置き換える。**
- **決定**: **維持**(Black/900)。ただし**ドキュメントの記述を訂正する**
  (`element-taxonomy-2026-08.md` A3-2 の「Bold(700)」は事実と違う)。
  実際の修正は A3-7 で行う。
- **根拠**: 上の実測表。加えて「太いフォントの欠点は、文字が小さいと線と線の間の余白がつぶれて
  逆に読みにくくなる」という一般則([ニィスフォント](https://www.nisfont.co.jp/blog/2016_05_25/) /
  [CreativeFlake](https://blog2.creativeflake.com/2016/08/05/%E5%A4%AA%E5%AD%97%E3%81%AB%E3%81%97%E3%81%A6%E3%82%82%E6%96%87%E5%AD%97%E3%82%92%E6%BD%B0%E3%81%95%E3%81%AA%E3%81%84%E6%96%B9%E6%B3%95%E3%80%8C%E5%A4%AA%E5%AD%97%E3%81%AB%E5%BC%B7%E3%81%84%E7%84%A1/))
  と方向は一致するが、**うちの55.6pxは「小さい文字」ではない**ので、
  ウェイトを落とす理由にはならない。落とすべきは縁取りの方。
- **確度**: **A**(ウェイトの実体が Black/900 であることは `findfont` で再現確認済み。
  `FontProperties(family='Noto Sans CJK JP', weight='black')` → `NotoSansCJK-Black.ttc`、
  `weight='bold'` → `NotoSansCJK-Bold.ttc`)

## A3-3 サイズ

- **現状**: `SUB_FS = 40`(pt)。`DPI = 100` なので実px = `40 × 100/72 = 55.6px`。
  1080pxに対して **5.14%**。(縦型は52pt = 72.2px / 1920px = 3.76%)
  **訂正対象がもう2箇所ある**: `element-taxonomy-2026-08.md` A3-3 の「40pt=画面高4.9%」と、
  `shortlib.py` の `use_landscape()` docstring 内「少し大きめの40pt(4.9%)」。
  どちらも正しくは **5.14%**。
- **選択肢**:

  | 案 | 内容 | 採用例・出典 | 長所 | 短所 |
  |---|---|---|---|---|
  | ① 40pt = 画面高5.14%(現状) | — | [WebVTT既定のキュー文字サイズは **5vh**](https://github.com/w3c/webvtt/issues/371) | ブラウザ字幕の既定とほぼ同一。TVでも十分 | — |
  | ② 32pt = 4.1% | CEA-608換算 | [608→WebVTT変換: 行高5.33%、文字は行高÷1.3 = 約4.1%](https://dvcs.w3.org/hg/text-tracks/raw-file/default/608toVTT/608toVTT.html) | 図に取られる面積が減る | 26字で組むと1行が細く見える。TVで小さい |
  | ③ 44〜48pt = 5.7〜6.2% | 大きめ | 縦型・モバイル優先の慣行(1行20字以内・[スマホで36px以上](https://video-ai-guide.com/category-design/design-01-text.html)) | スマホの横型視聴で有利 | 26字が1行に入らなくなり `block_fit` の自動縮小が頻発、ユニット間で字の大きさが揺れる |
  | ④ 内容で可変 | 短い文は大きく | 一部のYouTube編集 | メリハリ | 「ユニット内で文字サイズが揃う」という既存方針(`block_fit`)を壊す |

- **比較の軸**: 規格の既定値との一致 / TV(10フィート)での可読 / 26字が1行に収まるか / 実装コスト
- **決定**: **維持**(40pt)
- **根拠**:
  - WebVTT のキュー文字サイズの既定は **5vh** で、うちの 5.14% はほぼ一致
    ([w3c/webvtt#371](https://github.com/w3c/webvtt/issues/371))
  - CEA-608 由来の下限(約4.1%)と、モバイル寄りの上限(6%前後)の**ちょうど間**にある
  - TV視聴側: Fire TV の10フィートUIガイドは 1080p で **最小28px**
    ([Game Accessibility Guidelines](https://gameaccessibilityguidelines.com/use-an-easily-readable-default-font-size/) /
    [10-foot user interface](https://en.wikipedia.org/wiki/10-foot_user_interface))。55.6px はその**2倍**
  - 26字 × 55.6px = 1445px = 画面幅の75%。`SUB_BLOCK_FIT = 0.86`(1651px)に収まるので、
    **実測で L001 の1行最大は26字、自動縮小は0件**。上げると縮小が始まる
  - **視聴デバイスの内訳データはユーザーのStudioから取れていない。** モバイル比率が
    分かればここは実測で詰められる(いまは規格からの推定 = 確度B)
- **⚠ 検証(反証担当)**:
  - 「`block_fit` の自動縮小は0件」を再現確認した。L001 の全113ユニットを
    `wrap_rich` → `_measure_widths` に通すと、最長行の実測幅が `SUB_BLOCK_FIT = 0.86` を
    超えるユニットは **0/113**。この記述は正しい(が、A3-14 が同じ事実を逆に書いている。後述)
  - 一方で **WebVTT の「既定5vh」を根拠に使うなら、A3-6 の「行送り比1.30」とは両立しない**。
    issue #371 の本文を実際に取得したところ、原文は
    "The default font size is 5vh, however the default line spacing for addressing line
    positions is only 5.33vh, representing a line spacing of **106.6%**" だった。
    つまり同じ規格の中では **font 5vh・行送り比 1.066**。
    調査員は A3-3 で「5vh」、A3-6 で「1.30」と、**別々の前提から都合のよい側だけを引いている**。
    A3-3 の 5.14% ≒ 5vh という一致自体は成立するので決定は維持するが、
    根拠は「WebVTT既定 5vh と一致(**ただし同時に A3-6 の根拠にはできない**)」と書き直す
- **確度**: **B**

## A3-6 行間

- **現状**: `SUB_LINE_H = 0.069`(図の高さに対する割合)。
  実px = `0.069 × 1080 = 74.5px`。文字のem = 55.6px なので **行送り比 = 1.34**。
  `draw_rich_text()` は `y - i * line_h * (fontsize/40)` で送るので、
  字が縮んでも行送りが比例して縮む(=比は保たれる)。
- **選択肢**:

  | 案 | 内容 | 採用例・出典 | 長所 | 短所 |
  |---|---|---|---|---|
  | ① 1.34倍(現状) | 74.5px | [CEA-608→WebVTT: 行高5.33% / 文字はその÷1.3 → 行送り比 **1.30**](https://dvcs.w3.org/hg/text-tracks/raw-file/default/608toVTT/608toVTT.html) | 規格の換算値とほぼ同じ | — |
  | ② 1.15〜1.2倍 | 詰める | 見出し組みの慣行 | 2行が1かたまりに見え、帯を薄くできる | 「密着させない」という一般則に反する。漢字は字面が大きいので特に詰まって見える |
  | ③ 1.5倍 | 空ける | 本文組みの慣行 | ゆったり | 2行が別々のテロップに見え始める。帯の高さが要る |

- **比較の軸**: 規格の換算値との距離 / 2行が1かたまりに見えるか / 帯の高さ
- **決定**: **維持**(0.069 = 行送り比1.34)。**ただし「規格と一致している」という根拠は取り下げる。**
- **⚠ 検証(反証担当) — この項目の根拠は崩れた**:
  - 唯一この環境から本文を取得できた出典が [w3c/webvtt#371](https://github.com/w3c/webvtt/issues/371) で、
    原文はこうだった:
    > "The default font size is 5vh, however the default line spacing for addressing line
    > positions is only 5.33vh, representing a line spacing of **106.6%**"
  - つまり **WebVTT 既定の行送り比は 1.066** であって 1.30 ではない。
    そして issue #371 は**まさにその1.066が詰まりすぎて "strange effects" を起こす**という
    問題提起であって、推奨値の提示ではない(normative な記述ですらない)。
  - 調査員が引いた 1.30 は 608toVTT の「文字サイズ = 行高 ÷ 1.3」から来ているが、
    それは**文字を 4.1% に縮める前提**の比であり、A3-3 で採った「文字 5vh」とは前提が違う。
    **A3-3 と A3-6 は、同じ規格群から互いに両立しない数字を1つずつ持ってきている。**
  - 608toVTT の本文はこの環境から egress で遮断され、**検索スニペット以上の確認はできていない**。
  - うちの実測: `0.069 × 1080 = 74.5px`、em = 55.56px → **行送り比 1.341**(再現確認済み)。
    これは WebVTT 既定の 1.066 より **26%緩い**。
  - 残る事実は「**日本語テロップの行間に数値を挙げた定石は見つからない**」の1点だけ。
    選択肢②③に至っては出典欄が「見出し組みの慣行」「本文組みの慣行」で、**出典が無い**。
- **根拠**: 実質、**根拠は無い**。1.341 という値は縦型からの px 換算の副産物であり、
  規格の裏付けは取れなかった。**維持するのは「変える根拠も無い」からであって、
  「規格に合っているから」ではない。**
- **確度**: **C**(実装値 0.069 と行送り比 1.341 の実測は A。
  「その値が適切」という主張は出典1本・しかも反証側の文脈なので **C**)。
  → research-standards.md §4 に従い、**行間は行動変更に使わない**。A/Bテスト送り。

## A3-7 縁取り

- **現状**: `stroke_fx(text_color, outline, fatten=2.0)` が3層を積む。
  ```
  Stroke(linewidth=outline, foreground="#000000")   # 黒
  Stroke(linewidth=fatten,  foreground=text_color)  # 文字と同色(既定 2.0pt)
  Normal()                                          # 塗り
  ```
  `outline_for(fs) = fs × 0.10` なので 40pt なら outline = 4.0pt。
  **重要**: matplotlib の `Stroke` は輪郭の**中心**に引かれるので、
  - 黒: linewidth 4.0pt = 5.56px → 外側に **2.78px**(= em の 5.0%)
  - 同色 fatten: 2.0pt = 2.78px → 外側に **1.39px**
  - 結果: **文字が左右に1.39pxずつ太り、見える黒縁は 2.78px から 1.39px に痩せる**
  つまりドキュメントの「縁取り=文字サイズの10%」は**中心線の太さ**の話で、
  **外側に見える太さは5%**。ここが記述と実態のズレ。
- **実測(A3-2の表を再掲。40pt「確」。反証担当の再計測値)**: インク被覆は
  現状 **0.502** → `fatten=0` で **0.403**。counter の最大面積は **47px → 95px(2倍)**。
  `outline` 比を 0.10→0.00 まで振っても被覆は 0.403〜0.412 でほぼ動かない
  (=**黒縁の太さは潰れの原因ではない。これは反証担当も 0.10/0.08/0.06/0.04/0.00 の
  5点で再現確認した**)。目視でも「確」「第」「鑑」が現状では塊になっている。
- **⚠ 検証(反証担当)**: `stroke_fx` の描画順は
  `Stroke(黒, outline)` → `Stroke(同色, fatten)` → `Normal()` で、**黒が最下層**。
  つまり黒縁は glyph の内側にも `outline/2 = 2.78px` 食い込むが、その上を fill が覆う。
  counter(閉じた白場)には fill が来ないので**黒で埋まる**。
  ここで重要なのは、**現状の counter は「背景色」ではなく「黒」で埋まっている**こと。
  暗い背景(`SURFACE #1a1a19`)の上では黒も背景も見分けがつかないので実害は無いが、
  「白場が消える」の中身は「白場が黒くなる」ではなく
  「**fatten で左右から glyph が太り、counter の面積そのものが半分以下になる**」である。
  調査員の説明(中心線10% → 外側5%)は算数として正しく、再現確認した。
- **選択肢**:

  | 案 | 内容 | 採用例・出典 | 長所 | 短所 |
  |---|---|---|---|---|
  | ① 現状維持(黒4.0pt + 同色2.0pt) | — | — | 文字が太く見える | **漢字が潰れる(実測で白場0)** |
  | ② **fatten を 0 にする**(黒4.0ptのみ) | 1行の変更 | 自パイプライン実測 | 白場が全部戻る。他の描画への影響を字幕だけに閉じられる | 文字がわずかに細くなる(インク被覆 0.439→0.314) |
  | ③ fatten 0 + outline 比を 0.10→0.15 | 外側の黒を 2.78px→4.17px に | [縁取りは文字サイズの5〜10%](https://omniweb.jp/m25/) / [テロップデザインの教科書](https://freedoor.co.jp/blog/video-telop-design-guide/) / [YMM4のずんだもん字幕は6px・角縁取り](https://html-css-wordpress.com/zundamon-subtitles/) | 外側の黒が定石の中央値に来る。YMM4の定番(6px)に近づく | `outline_for()` は全テキスト共通なので、図のラベル・見出しまで太くなる。副作用が広い |
  | ④ 白フチ(黒文字) | 反転 | [白文字に黒縁が最も視認性が高い](https://omniweb.jp/m25/) | — | 定石が明確に否定 |

- **比較の軸**: 漢字の白場が残るか / 変更の副作用の広さ / 定石(5〜10%)の範囲内か
- **決定**: **変更 — `fatten` を `2.0 → 0.0` にする**(字幕経路)
  具体的には `draw_rich_line()` の
  `path_effects=stroke_fx(color, outline=outline)` を
  `path_effects=stroke_fx(color, outline=outline, fatten=0.0)` にする。
  `stroke_fx()` の既定値 2.0 は他の呼び出し元(`scenes_common.py` / `scenes_long.py` の
  20箇所以上)が明示指定で使っているので**そのまま残す**。字幕だけを直す。
  `outline_for()` の比 0.10 は**維持**(外側の実効は5% = 定石5〜10%の下限で範囲内)。
- **根拠**:
  - 実測: インク被覆 0.502 → 0.403、counter 最大面積 47px → 95px(40pt「確」)。**確度A**
  - 定石: 縁取りは文字サイズの5〜10%([omniweb](https://omniweb.jp/m25/)、
    [freedoor](https://freedoor.co.jp/blog/video-telop-design-guide/))。
    ③に上げるのは定石内だが、`outline_for()` は共通関数で副作用が広く、
    **潰れという実害を消すのに必要な変更は②だけ**。最小の変更で最大の効果を取る
  - 「太字にすると線と線の間の余白がつぶれる」という一般則とも整合
    ([ニィスフォント](https://www.nisfont.co.jp/blog/2016_05_25/))
  - ドキュメントも直す: 「縁取り=文字サイズの10%」→「中心線10% = 外側に見えるのは5%」
- **確度**: **A**

- **現状**: `pop=1.06`(1.06倍から等倍への収束)。**ただし実装が繋がっていない。**
  `render_video()` の該当箇所:
  ```
  if anim > 0:
      n = max(2, int(anim * u.fps))
      for k in range(n):
          emit(t, k, anim/n, pop=(1.06 if k == 0 else 1.0), ...)
  else:
      ...  emit(...)   # ← pop は既定の 1.0。渡されない
  ```
- **実測(L001・113ユニット)**:

  | 計測 | 値 |
  |---|---|
  | `anim = 0` のユニット(= pop が一度も起きない) | **59本 / 113本 = 52%** |
  | pop が起きるときの持続 | `anim/n = 1/fps = **0.05秒**`(fps=20) |

  → **半分のユニットには演出が無く、残り半分も0.05秒の1フレーム。実質存在しない。**

  **⚠ 検証(反証担当)**: 実測は AST で再走査して**完全一致**で再現した
  (anim の分布は `0.0` が59本・`1.4` が53本・`1.6` が1本、fps は全ユニット20。
  `n = max(2, int(anim*fps))` なので pop フレーム長は 1.4/28 = 1.6/32 = **0.0500秒**)。

  **ただし「`block_fit` の自動縮小が掛かる長い行ではその1フレームだけ字が縮む」は誤り。** 2つ間違っている:
  1. **L001 で `block_fit` がクランプするユニットは 0/113。** 最長行の実測幅が
     `SUB_BLOCK_FIT = 0.86` を超えるユニットは1本も無い。この副作用は**そもそも起きない**。
     しかも調査員自身が A3-3 の根拠欄で「**実測で L001 の1行最大は26字、自動縮小は0件**」と
     書いている。**同じ文書の中で同じ事実を逆に使っている。**
  2. 仮にクランプしても縮まない。`draw_rich_text()` の縮小は
     `fontsize = fontsize * block_fit / worst` で、`worst` は `fontsize` に**比例**するから、
     結果は `block_fit / (worst/fontsize)` となり **`pop` が約分されて消える**。
     つまりクランプ時の pop は「逆方向に効く」のではなく「**何も起きない(打ち消される)**」。
     行送りも `line_h * (fontsize/40)` で縮小後サイズを使うので同様。
     実際に L001 の全ユニットで pop=1.0 と pop=1.06 の最終 fontsize を出すと、
     非クランプでは 40.0 と 42.4、クランプ時は(発生しないが式の上で)完全に同値になる。
- **選択肢**:

  | 案 | 内容 | 採用例・出典 | 長所 | 短所 |
  |---|---|---|---|---|
  | ① 現状(実質なし) | — | — | 落ち着いている。焼き時間が最短 | 「出しっぱなしにしない」という定石を満たしていない。話者が替わっても画面が変化しない |
  | ② **全ユニットの先頭に pop を掛け、0.10〜0.15秒に伸ばす** | `anim` の有無に関わらず適用 | [ポップオンが最も一般的で基本的な字幕アニメーション](https://rendercut.io/best-caption-styles-retention-engagement) / [控えめなフェードインや軽いポップのほうが、動き続けるものより成績が良い](https://subtitlesfast.com/blog/subtitle-styles-that-convert/) | 話者の交替が視覚で分かる(A3-12 の補強にもなる)。実装は emit の引数1つ | 焼き時間が増える(静止区間にフレームが増える) |
  | ③ カラオケ式(語単位ハイライト) | 発話に合わせて1語ずつ色が変わる | ツール会社の集客ブログのみ([SubtitlesFast](https://subtitlesfast.com/blog/subtitle-styles-that-convert/) / [Braiv](https://braiv.co/features/karaoke-style-captions))。**⚠ どちらも本文未確認・「調査」の実体不明** | 短尺では最強という**主張**がある(裏付け無し) | **実装不能**。VOICEVOX のモーラ単位の時刻を保持していないうえ、1文=1ユニット構造と `wrap_rich` の段組みを全部作り直すことになる |
  | ④ フェードイン | alpha 0→1 | [フェードインは注目を集める基本効果](https://note.com/katsuhiro_endo/n/n91981b1a3819)(note のため本文未確認・スニペットのみ) | 静か | matplotlib で文字の alpha を段階描画するとフレーム数が要る。pop と同コストで効果は弱い |

- **比較の軸**: 実装可能性 / 焼き時間 / 話者交替の可視化 / 過剰演出にならないか

  3. ~~`pop` が `block_fit` の縮小と干渉しないよう、`draw_subtitle()` で

## 定石が見つからず、自チャンネルのA/Bテストに回す項目

3. **A3-13 字数速度** — 6.39字/秒(384字/分)が速すぎるかどうかの根拠が無い。

## この調査で使った自前の計測

再現手順を残す(すべて `videos/L001-nisa-son/output/L001.mp4` と `production/shortlib.py`):

- 縁取りの潰れ: 40pt「確」を4条件で描画し、80×62pxの領域で
  「インクでない連結成分のうち外周に触れないもの(= 字の内側の白場)」を数えた
  ⚠ **この計測は再現しなかった**(反証担当の再計測では個数がしきい値と字で大きく動く)。
  代わりに**インク被覆**(単調で安定)と**counter の最大面積**を使うこと
- 帯の実効: `ffmpeg -vf "fps=1/4,crop=1920:170:0:860"` で全編100枚を抜き、
  各フレームの30パーセンタイル輝度(= 文字を除いた地の明るさ)を取った
- 行数・字数: `render.py` の `Unit(...)` 第2引数を正規表現で抜き、
  `shortlib.wrap_plain(plain, 26)` に通した(=本番と同じ折り返し)
- コントラスト比: WCAG 2.x の相対輝度式。帯の地色は実フレームの実測値(RGB 18,17,15)を使用

### 再現しなかった・誤りだったもの(本文を修正済み)

1. **A3-6 の根拠が崩れた(最大の指摘)** — 唯一取得できた
   [w3c/webvtt#371](https://github.com/w3c/webvtt/issues/371) の原文は
   「default font size is 5vh / default line spacing 5.33vh = **line spacing of 106.6%**」で、
   **WebVTT 既定の行送り比は 1.066**。しかも issue はその1.066が詰まりすぎるという
   **問題提起**であって推奨ではない。調査員は A3-3 で「5vh」、A3-6 で「1.30」を引いており、
   **同じ規格群から両立しない数字を1つずつ都合よく取っている**。
   うちの 1.341 は WebVTT 既定より26%緩い。→ A3-6 を **B → C**、決定の根拠を「無い」に書き換え。
2. **A3-7 / A3-2 の「白場 0個 → 4個」が再現しない** — 別実装で「確」を測ると 1個 → 7個、
   インク被覆も 0.439/0.314 ではなく 0.502/0.403。しきい値を 60/120/180 と振ると個数が動き、
   字によっては逆転する(「段」)。**個数は判断材料にならない**。
   決定(fatten を外す)は支持するが、根拠を「インク被覆 +0.10 / counter 面積が半分以下」に置換。
3. **A3-11「立ち絵の下端(0.200)は帯の上端(0.2052)の上で重ならない」は誤り** —
   上下が逆で、**いま既に5.6px重なっている**。同文書の選択肢④の記述とも矛盾。
4. **A3-11 の副作用の洗い出しが足りない** — `scenes_long.py` は注記を y=0.212(`compare2`、

   「注記は枠の外に出す」という設計意図が壊れる。→ 位置変更は保留。
5. **`check_overlap.py` では 4 を検出できない** — 同ファイル54行の

### 手続き上の指摘(`research-standards.md` §4 違反)

「**確度C: 行動変更に使わない。自チャンネルのアナリティクスでA/B検証する仮説として扱う**」に対し、

### 検証で使ったコマンド(再現用)

- 帯の実効: `ffmpeg -vf "fps=1/4,crop=1920:170:0:860"` で100枚 → 各フレームの30パーセンタイル輝度
- タグ色/字の色: `ffmpeg -ss 60/-ss 200 -frames:v 1` の実フレームから x=0〜11px / 中央帯域を平均
- 潰れ: `stroke_fx` を直接呼んで 40pt の漢字6字を4条件×しきい値3種で描画、
  BFS で「外周に触れない非インク連結成分」を数える
- ユニット統計: `ast.parse` で `Unit(...)` を拾い、`shortlib.wrap_plain` / `wrap_rich` /
  `_measure_widths` に本番と同じ引数で通す
- ウェイト: `font_manager.findfont(FontProperties(family=..., weight=...))`
