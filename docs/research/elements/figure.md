  Mayer の合図の原則 / 実装コスト。
- **決定**: **変更**(色数は増やさない。増やすのは「塗りの有無」という次元)。
  1. `MUTED_BAR` を `#67655f` → **`#6e6c65`**(背景比 2.99:1 → **3.31:1**)。
     `[検証]` **これは案B(グレーを明るくする)そのもので、単独では悪化する。**
     `default` の EMPH/MUTED_BAR は **3.18 → 2.86** に落ち、
     いま唯一通っている系統が落ちる。**下の 2. と抱き合わせでしか採ってはいけない**、
     という条件を明記しないと、1.だけ先に入れて悪くなる。
  2. **文脈の棒はベタ塗りをやめる。**
     `[検証]` **前版の書き方ではそのまま実装すると壊れる。**
     matplotlib の `Patch(alpha=0.30)` は **face だけでなく edge にも掛かる**ので、
     `facecolor=MUTED_BAR, alpha=0.30, edgecolor=MUTED_BAR` と書くと
     **枠線も 30% になり、背景比 1.37:1 で事実上見えなくなる**(計算値)。
     正しい書き方は **面だけを RGBA で薄くし、枠は不透明のまま**にすること:

     ```python
     from matplotlib.colors import to_rgb
     ghost = (*to_rgb(MUTED_BAR), 0.30)          # 面だけ 30%
     Rectangle(..., facecolor=ghost, edgecolor=MUTED_BAR, linewidth=2.2)  # alpha= は渡さない
     ```

     `[検証]` この形なら実効値は **枠 3.31:1(対背景)/ 主役の棒 対 薄い面 4.59〜6.33:1**
     で、5系統すべてが 3:1 を満たす。**ただし「主役の棒 対 枠線そのもの」は 1.90〜2.62 で通らない。**
     成立の根拠は「枠が背景と 3:1」「主役の面が薄い面と 3:1」であって、
     前版の「5系統すべてで成立する」は**どの面とどの面かを言っていないので不正確**。
  3. **図の主役色として `GOLD` を使うのをやめ `EMPH` に統一**する。
     L001 の compare2 が渡している `GOLD` が該当。
     GOLD/MUTED_BAR は最良でも 1.90:1 で、どの系統でも基準に届かない。
     `[検証]` **`band()` に同じ置換をしてはいけない。**`band` は
     **part を GOLD、rest を EMPH** で塗り分けており、
     GOLD を EMPH に替えると **part と rest が同じ色になって塗り分けが消える**。
     `band` の正しい直し方は:
     **part = EMPH(ベタ)/ rest = MUTED_BAR のゴースト(面 α0.30 + 不透明枠)**
     に置き換え、「全体の帯」と「rest」を1つにまとめること。
     これで part 対 rest は **3.35〜4.91:1**(新 MUTED_BAR。5系統すべて 3:1 以上)、
     part の上の SURFACE 文字も **6.29〜8.67:1** に上がり、2つの基準割れが同時に直る。
  4. `barsN(highlight=...)` を**必須引数にする**。現状 `highlight=None` だと**全部の棒が EMPH**
     になり(L001 の `uchiwake` がそれ)、合図が1点に絞れていない。
- **根拠**: WCAG 2.2 SC 1.4.11 Non-text Contrast(意味を持つ図形は隣接色と3:1)
  https://www.w3.org/TR/WCAG22/#non-text-contrast 。
  上の比率はすべて実装値から計算したもので、推定ではない。
  赤青を損益に割り当てない判断は、日本の株式慣習(赤=上昇)と世界標準(緑=上昇)が
  逆であることによる。
  「4色以内」という前版の定石は CUD の解説
  (https://cudo.jp/?page_id=1565 / https://www.dic-graphics.co.jp/navi/color/ud.html)
  に「3色なら赤・青・緑」「最大7色まで」とはあるが、**「グラフは4色以内」という一次資料は
  見つからなかった**。前版の「4色以内(B)」は根拠を1段落として扱う。
- **確度**: **A**(コントラスト比は実装値からの計算。検証員が独立に再計算して全数一致)。
  `[検証]` ただし **WCAG 2.2 SC 1.4.11 の本文は今回 w3.org が egress 遮断で読めていない**。
  「意味を持つ図形は隣接色と 3:1」という要件そのものは広く知られた内容だが、
  **本文照合済みではない**。数値の計算 = A、要件の引用 = B とするのが正確。
  「枠だけの棒にすると視聴維持が上がる」根拠は無い。効果ではなく**基準適合**が理由で、
  `hold-rate-2026-08.md` §6「見た目だけの変更を維持率施策と呼ばない」とも整合する。

## A5-3 マーク仕様

- **現状**:
  - `barsN`: `Rectangle`、**角丸なし**、`alpha=0.95`、`edgecolor="none"`。
    棒幅 `bw = min(0.115, slot*0.62)`、`slot = 0.720/n`。
    - n=6 → slot 0.120、bw **0.0744**(143px)、隙間 0.0456(88px)、**gap/bar = 61%**
    - n=2 → slot 0.360、bw **0.115**(221px)、隙間 0.245(470px)、**gap/bar = 213%**
  - 底のベースラインは `MUTED` の 1.5px 実線、alpha 0.5。y軸目盛りは無し(直接ラベル)。

## A5-4 数値ラベル

- **現状**: 課題文の「図内で最大級のサイズ」は**事実ではない**。実測は上の表のとおり:

  | | pt | px | 字幕(55.6px)との比 |
  |---|---|---|---|
  | barsN の数値 | 30 | 41.7 | **0.75倍(字幕より小さい)** |
  | compare2 の棒ラベル | 26 | 36.1 | **0.65倍** |
  | compare2 の合計 | 34 | 47.2 | 0.85倍 |
  | table の数字 | 34 / 30 | 47.2 / 41.7 | 0.85 / 0.75倍 |
  | timeline の値 | 36 | 50.0 | 0.90倍 |

  どちらも字幕より小さい。「数字が主役」は実装されていない。
- **もう1つの実測の不具合**: `barsN` は `S.text_fit(..., inner, fontsize=30)` を

  clamp していない。6本 × 8文字のラベルで実測すると:

  '11万3877円' x0=0.4141 x1=0.5359   ← 0.0018 (3.5px) 重なっている

  **「6本 × 8文字の金額ラベル」という合成ケース**であって、

  **「その8文字ラベルを6本並べたら重なる」は幾何として正しく、直す価値はある**。
  ただし根拠は「起きている不具合」ではなく「起こしうる欠陥」。**確度は A から B に下げる。**

## A5-5 登場アニメ

- **現状**: `Unit.anim` は L001 で 1.4 / 1.6、L002 で 1.4 / 1.6 / 1.8 / 2.0 / 2.2。

## A5-6 図が無い時間

- **現状**: `check_long.py` の不合格条件「図が出ないユニットの連続が **25秒**を超えたら不合格」。
  図かどうかは `FIGURE_KINDS` の7種で判定する。
- **実測で見つかった重大な不具合**: `check_long.scene_kinds()` は
  `re.search(r'"key":\s*s[cl]?\.?(\w+)', src)` という**正規表現でソースを読んでいる**。
  そのため **ヘルパー関数経由で組み立てたシーンは型が `?` になり、図として数えられない**。
  `[検証]` **関数名が違う。**L002 のヘルパーは `_ichiran()` ではなく
  **`_bars(upto, highlight=None)`**(render.py 53行目)で、
  これが返しているシーンキーは **`be5` / `be10` / `be15` / `be20` / `be25` の5キー**。
  この5キーが付いた **10 ユニットが「図なし」として計上されている**
  (`scene_kinds()` の戻り値でこの5キーだけが `"?"` になることを実行して確認した)。
  L002 の図の割合は 53/155 = 34% と出るが、実際は 63/155 = 41%。
  `[検証]` 実行して一致(regex 版 53、`__qualname__` 版 63)。
  **L001 側は 71 で一致し、影響を受けない**(L001 はヘルパーを経由していない)。
  「図なしの連続25秒」の判定も同じぶんだけ厳しく出ている。
- **外の目安**:

  | 出どころ | 主張 | 質 |
  |---|---|---|
  | 日本語の動画編集解説 | **5〜10秒に1回**は何らかのカット・画面遷移・動きを入れる。冒頭3秒で視覚的な動きを2〜3回 | 実務ブログ。相互コピペ多数=独立ソースとしては1本 |
  | 英語圏の retention 解説 | pattern interrupt は **20〜40秒に1回**。長い区間なら **60〜90秒に1回**は画面上の何かを変える | 同上。数字が資料間で 20〜90 秒とばらける |
  | 自チャンネル | 25秒 | 由来の記録は `longform-design.md` にあるが、外部の根拠は示されていない |

- **選択肢**:

  | 案 | 内容 | 長所 | 短所 |
  |---|---|---|---|
  | A 現状維持 25秒 | — | 実績がある(L001 が通っている) | 外部の根拠が無い。20〜90秒のどこを取ってもよい |
  | B 15秒に厳しくする | 日本語の編集慣行(5〜10秒)寄り | 画面が動き続ける | **量で通せるゲートになる。**飾りの図を足せば通る。`check_long.py` 自身が禁じている失敗 |
  | C 40秒に緩める | 英語圏の pattern interrupt 上限寄り | カードで語る場面を作れる | 図が主役という方針と逆行 |
  | D 閾値は据え置き、**計測の欠陥を直す** | 型判定を実行時の関数名から取る | 嘘の数字でゲートを回さなくなる | 直すと L002 の判定が変わる |
  | E 「同じ図が何ユニット続いたか」を別に測る | 図はあるが**中身が変わらない**時間を見る | 「図はあるが動いていない」を捕まえられる | 新しい WARN が1つ増える |

- **比較の軸**: 量で通せないゲートか / 計測が正しいか / 外部の根拠の強さ /
  「図が主役」という方針との整合。
- **決定**: **変更(閾値は維持、計測を直す)**。
  1. **25秒は維持。**外部に一次資料が無く、20〜90秒のどこを取るかを決める根拠が無いため、
     動かす理由が無い。**「25秒に定石の裏付けがある」という前版の判定(実測A)は撤回する。**
     これは自チャンネルが決めた値であって定石ではない。
  2. **`scene_kinds()` を実行時の関数名から取るように直す**(具体コード):

     ```python
     def scene_kinds(src, scenes):
         out = {}
         for key, fn in scenes.items():
             qn = getattr(fn, "__qualname__", "")          # "barsN.<locals>.painter"
             if "<locals>" in qn:
                 out[key] = qn.split(".<locals>.")[0]
             else:
                 m = re.search(r'"' + re.escape(key) + r'":\s*s[cl]?\.?(\w+)', src)
                 out[key] = m.group(1) if m else "?"
         return out
     ```

     `scenes_long` の描画関数はすべて内側で `painter` を定義して返すクロージャなので、
     `__qualname__` に元の型名がそのまま残る。ヘルパー経由でも正しく取れる。
     `[検証]` **このコードを実際に L001/L002 に当てて動作を確認した。**
     L001 は regex 版と完全一致、L002 は `be5〜be25` の5キーが `?` → `barsN` に直る。
     **`scenes_common`(縦型)も同じクロージャの形なので副作用は無い**が、
     `check_long.py` は横型専用なのでそもそも縦型には掛からない。
  3. **WARN を1つ追加**: 同じ scene キーが **5ユニット以上**続いたら
     「図が出っぱなしで中身が変わっていない」と出す。
     実測では L001 `uchiwake` が5、L002 `sagasu2` が6で、どちらもここに当たる。
     `[検証]` 最長連続は L001 = 5、L002 = 6 で一致。
     ただし **`uchiwake` の5連続は anim=1.4 の1本と anim=0.0 の4本**で、
     「同じ図の上で数字を1つずつ言う」という意図的な作りである
     (`longform-design.md`「数字は図の上で言う」に沿っている)。
     **これを一律に WARN にすると、方針に沿った作りを咎めることになる。**
     WARN の条件は「同じキーが5連続」ではなく
     **「同じキーが5連続 かつ その区間の合計秒が25秒を超える」**にすべき
     (図なしの上限と同じ秒数に揃える)。
  4. A5-1 の決定により `checklist` を `FIGURE_KINDS` から外すので、
     「箇条書きを4枚めくれば25秒ゲートを永久に回避できる」抜け道が塞がる。
- **根拠**: 日本語の編集慣行 —
  https://reelgrow.jp/blog/long-video-never-get-bored/ /
  https://birdy-official.co.jp/youtube-retention-tips/ /
  https://coconala.com/blogs/5202455/767960 。
  英語圏 — https://air.io/en/youtube-hacks/advanced-retention-editing-cutting-patterns-that-keep-viewers-past-minute-8 /
  https://narrationbox.com/blog/why-viewers-drop-off-after-30-seconds-youtube 。
  **いずれも実務ブログで、数字の出どころ(実測データ)は示されていない。**
  YouTube公式ヘルプに「何秒ごとに画面を変える」という記述は見つからなかった。
  計測の不具合は自リポジトリで render.py を import して確認した。
- **確度**: 閾値 25秒 = **C**(定石は存在しない。自チャンネルの A/B で検証する対象)。
  `[検証]` **この撤回(前版の「実測A」→ C)は妥当で、支持する。**
