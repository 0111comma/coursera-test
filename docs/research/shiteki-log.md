# 指摘ログ — 生のまま貯める場所

ユーザー指示(2026-08-31):
> 「今回出た指摘とかはちゃんと貯めておいてね。あとで貯められた指摘を
>   抽象化してルールにするとかできるから」

**ここは抽象化する前の生の指摘を貯める場所。**
`design-rules.md` / `kotoba-rules.md` は蒸留した後のルール集で、
そこに載せるかどうかを判断する材料がここに溜まる。

## 使い方

- **審査・テストで出た指摘は、その日のうちにここへ追記する。**要約しない。
  「誰が」「何を見て」「何と言ったか」を残す。言い回しを丸めると、
  あとで抽象化するときに元の温度が分からなくなる
- ユーザーの生の言葉は**引用符で原文のまま**残す。これがいちばん価値がある
- 「どう直したか」と「直した結果どうなったか」まで書く。
  直して悪化したものは、それ自体が知見
- 3回以上くり返し出た指摘には ⚠️ を付ける。ルール化の第一候補

## 抽象化の判断(いつルールにするか)

1. **2本以上の動画で出た** → ルール化を検討する
2. **同じ動画で2回以上再発した** → ルール化する(直し方が定着していない証拠)
3. **機械で判定できる** → ゲート化する(`check_*.py`)。
   ただし偽陽性を出すゲートは信用を壊すので、実測で検証してから入れる
4. 1本きりの事情 → ここに置いたままにする

## 抽象化の候補(まだルールにしていない)

- ⚠️ **尺のために文を短くしない。削るならユニットごと落とす。**
  断片だけ残すのがいちばん悪い(A)
- ⚠️ **「分かりやすいか」を意見で聞かない。理解度を問題で測る。**
  素人役に書き換え案を書かせると専門家に戻る(B)
- ⚠️ **改稿は声と画面の両方に通す。**片方だけ直して「直した」としない(D)
- **視聴者が「知らない」と答えた語は、声から外して図に置く**。
  説明を足すのではなく、判定に要らないなら捨てる(#2)
- **途中式を見せる尺のない数字は出さない。**
  出どころの分からない数字は、そこから先の理解を止める(#3)
- **手順を渡す前に自己適用を求めない。**
  「あなたはどう?」は、計算方法を渡したあとに置く(#4)
- **同じ規則を複数回あてるときは、言い回しまで同じにする。**
  音だけで追えるようにする(#12)
- **テストの質問は、テスト対象の版に合わせて作り直す**(C)
